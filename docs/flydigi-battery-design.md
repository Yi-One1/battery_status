# 飞智冰原狼 4 电量读取 — 需求澄清与设计方案（v2）

> 状态：**需求已变更 —— 你要求"不切模式也能实时看"，而这一点在 XInput 模式下不可得。**
> 本文把"为什么不可得"和"还剩哪几条路"讲清楚，等你选一条。
> 日期：2026-10-20　基线：`b4ead22`

---

## 0. 结论先行

**XInput 模式下，这台手柄没有把电量交给系统的任何通道 —— 不是我们读得不对，是数据不在那儿。**

三条彼此独立的证据（见第 1 节）都指向同一件事：手柄在 2.4G/XInput 模式下，
Windows 里只有一个由微软 `xusb22` 驱动接管的标准 Xbox 360 手柄接口，
它没有输出端点、没有 feature 端点、也没有厂商 Usage Page。
**没有下行通道，就意味着发不出任何"报一下电量"的请求。**

所以"不切模式 + 实时百分比"这个组合，在**当前连接方式**下是做不到的。
要么换连接方式（蓝牙 / 有线），要么接受"无线时没有数字"。

## 1. 证据链（全部在真机验证）

| # | 事实 | 证据 |
|---|---|---|
| 1 | XInput 把它报成"有线供电 + 满档" | `BatteryType=1(WIRED)`、`BatteryLevel=3`；`XInputGetCapabilities.Flags=0x0000`（无 `WIRELESS` 位） |
| 2 | 手柄接入后，PnP 里**只多出一个**设备 | `USB\VID_045E&PID_028E\FLYDIGI_DIREWOLF_4`，单接口（没有 `MI_xx`，不是复合设备），服务 = `xusb22` |
| 3 | 那个 HID 接口**没有下行能力** | `IN=15`、`OUT=0`、`FEAT=0` —— 只能收，不能发 |
| 4 | WinRT 的两套手柄 API 都看不到它 | `Windows.Gaming.Input.Gamepad.Gamepads` → 0；`RawGameController` → 0（xusb22 设备不在 WinRT 枚举范围） |
| 5 | Space Station 的通道是**单实例命名管道**，外部连不进去 | `CreateFileW("\\\\.\\pipe\\fcs.sock")` → `err=231 ERROR_PIPE_BUSY` |
| 6 | 它的服务进程**不碰 HID**（25 秒观察零调用） | 说明设备被驱动层直接接管，HID 栈上自然没有厂商集合 |
| 7 | 协议本身是公开的，但我们没有通道去发 | SDL `SDL_hidapi_flydigi.c`：V1 `05 EC`、V2 `03 5A A5 01 02 00` |

### 一处必须纠正的错误

上一版方案里我把 `2BDF:028A` 当成了"飞智接收器本体"，**这是错的**。
PnP 显示它是一个 **HIK 2K 摄像头**：

```
USB\VID_2BDF&PID_028A&MI_00  → HIK 2K Camera      (usbvideo)
USB\VID_2BDF&PID_028A&MI_02  → HIK 2K Camera-Audio (usbaudio)
USB\VID_2BDF&PID_028A&MI_04  → USB 串行设备 COM3   (usbser)
USB\VID_2BDF&PID_028A&MI_06  → HID-compliant device (HidUsb)
```

它手柄关机时也在、对它发 `05 EC` 只回一个计数器 ack —— 全都解释得通了。
**这条线索作废**，我之前"2BDF 是飞智另一个设备"的推断也是错的。

## 2. 目标 / 非目标（按你的新要求重述）

**目标**
- G1 手柄在**正常打游戏的状态**（2.4G / XInput）下，尽量让界面上的信息有用
- G2 绝不显示假数据（不猜、不按时长估算、不把满档当 100%）
- G3 任何新增通道都必须"读不到就干净退回"

**非目标**
- N1 不做驱动级逆向、不装内核驱动、不做 USB 总线抓包
- N2 不要求卸载飞智驱动
- N3 **不要求你为了看电量而切模式**（这是本次新增的硬约束，方案 A 因此作废）

## 3. 只剩这四条路

| | 能在 XInput 下实时读？ | 需要你做什么 | 代价 | 我的判断 |
|---|---|---|---|---|
| **有线 USB（插线）** | ❌ 无线时不行，**插线时可能可以** | 插一次数据线（充电本来就要插） | 无（插线时本来就在充电） | **优先验证**，SDL 的 HID 驱动就是为有线/直连写的 |
| **蓝牙连接** | ✅ 能（Windows 原生报电量） | 改用蓝牙配对，不再用接收器 | 游戏延迟、部分游戏兼容性变差 | 可行但不推荐作为默认 |
| **记忆 + 时间戳** | ⚠️ 不是实时，但**永远有数** | 无 | 数字会变旧 | **建议作为兜底**，和上面任一条配合 |
| **切 DInput** | ✅ 能 | 切模式 | 打游戏要切回来 | 你已否掉 |

> 如果四条都不接受，那就只能回到现状：XInput 模式下显示「2.4G 连接」+ 暂无电量。

### 为什么"记忆 + 时间戳"值得做

它单独不能解决"实时"，但它能让另外三条路的收益**不被浪费**：
只要在任何一个可读时刻（插线 / 蓝牙 / 你哪天切了 DInput）读到过电量，
之后切回无线也能显示「上次 62% · 2 小时前」，而不是一句干巴巴的「暂无电量」。
界面上把"这是多久以前的数据"写清楚，就不会误导人 —— 这和本项目一贯的"宁可没有数字，也不编数字"是一致的。

## 4. 建议的组合方案

```
来源优先级（同一台设备，谁有数据用谁）
  ① 有线厂商通道（插线时，实时）        ← 待验证
  ② 蓝牙 GATT 电量（若你选蓝牙）        ← 可选
  ③ 上次读到的值 + 时间戳（缓存）      ← 兜底，新增
  ④ 都没有 → 「2.4G 连接」+ 暂无电量    ← 现状
```

对应到界面：

| 情形 | 电量 | 状态行 |
|---|---|---|
| 插线且读到 | 62% | 有线 · 充电中 |
| 无线，有缓存（2 小时前） | 62% | 2.4G 连接 · 2 小时前 |
| 无线，无缓存 | -- | 2.4G 连接 |
| 关机 | -- | 未连接 |

## 5. 前置验证（需要你 30 秒，插一次线）

在写任何代码之前，必须先确认"有线模式到底有没有厂商通道"：

1. 你把手柄用**数据线**接到电脑（**不用动模式开关**，插上就行）
2. 我跑 `usb_probe.py list`，看是否新出现 `2BDF` / `37D7` / 非 `045E:028E` 的厂商接口
3. 若有：发 `05 EC`（V1）与 `03 5A A5 01 02 00`（V2），抓 32/64 字节应答
4. 拿 Space Station 显示的数字**对表** —— 对上了才算证据

**结果处理**
- 对得上 → 落地"有线实时 + 无线记忆"（改动：`devices.json` + `protocols.py` 一处 + 缓存字段 + 约 8 项测试）
- 对不上 → 有线这条路也关掉，只剩蓝牙或现状；我会把结论写进 README 的"已知限制"，不再反复
