## 0. 一句话结论

**在"保持 XInput 模式 + 装着飞智驱动"的前提下，拿不到电量，这不是实现问题，是信息不在那里。**
要拿到百分比，必须三选一：让手柄暴露厂商接口（动手柄上的模式开关）、借用飞智自己的进程（脆弱），
或者接受"只报连接状态"。**我建议：以"只报连接状态"为默认基线（当前已是这个状态），把 DInput 模式做成一个可选、可回落的实验路径。**

## 1. 现状与证据

以下每条都在真机上验证过，不是推断：

| # | 事实 | 证据 |
|---|---|---|
| 1 | 手柄以 2.4G 连上后，系统里**只多出一个标准 Xbox 手柄接口** | `045E:028E if=0`，UP=0x0001 U=0x05，IN=15 字节、**OUT=0**（没有下行通道，发不出任何厂商命令） |
| 2 | XInput 把它报成"有线供电 + 满档" | `BatteryType=1(WIRED)`、`BatteryLevel=3`、`XInputGetCapabilities.Flags=0x0000`（**无** `WIRELESS` 位） |
| 3 | 手柄关着时 `2BDF:028A` 也在，说明它是接收器本体而不是手柄 | 关机状态下仍枚举到；MI_06，UP=0x0081，IN/OUT=1024 字节 |
| 4 | 对这条 1024 字节通道发 V1/V2 探测（`05 EC`、`03 5A A5 01…`）只回一个空 ack | 回帧 `01 5A 5A 00 00 00 00 00 03 00 00 00 A3 01…`，除计数器外全 0，没有 0..100 的值 |
| 5 | Space Station 是 **Electron UI + 原生服务**，两者走命名管道 | 日志：`connect ENOENT \\?\pipe\fcs.sock`；进程：`Flydigi Space Station.exe` ×5 + `SpaceStationService.exe` |
| 6 | 这条管道是**单实例**，外部连不进去 | `CreateFileW` → `err=231 ERROR_PIPE_BUSY`（仅 Space Station 自己在用） |
| 7 | 服务进程**不碰 HID** | 对 `SpaceStationService` 挂 `CreateFileW / WriteFile / ReadFile / DeviceIoControl` 观察 25 秒，零 HID 打开 |
| 8 | 所以设备被**驱动层**（内核）接走了，HID 栈上自然看不到厂商集合 | 由 3 + 7 反推：这是"只有标准 Xbox 接口、没有厂商接口"的直接原因 |
| 9 | 协议本身是公开的 | SDL 的 `SDL_hidapi_flydigi.c`：V1 写 `05 EC`；V2 写 `03 5A A5 01 02 00`，应答 `data[11]` 高 4 位=充电状态、低 4 位=档位×20 |

**一句话：我们不缺协议，缺的是"能发命令的那条通道"。**

## 2. 目标 / 非目标

**目标**
- G1 手柄接上后，界面上不再出现错误状态（已达成：不再谎称"充电中"）
- G2 在**不改动用户既有使用方式**的前提下，尽可能显示真实电量
- G3 任何新增能力都必须"读不到就干净地退回原状"，不许出现假数据

**非目标**
- N1 不做驱动级逆向（不装内核驱动、不 hook 驱动、不碰 USB 总线抓包）
- N2 不要求用户卸载飞智驱动（那会连 XInput 一起废掉）
- N3 不为了一台设备改变全局扫描节奏（低占用是硬约束）

## 3. 需求澄清（需要你拍板）

### Q1（最关键）手柄的模式开关，你愿意为"看电量"动它吗？

冰原狼 4 有一个硬件模式开关（XInput / DInput / BT / Switch）。**XInput 是给游戏用的，DInput 才会暴露厂商 HID 接口。**

- 选 **A：愿意偶尔切** → 走方案 A，我能给你精确百分比，但**只在 DInput 模式下有**；打游戏时切回 XInput 就又只有"已连接"。
- 选 **B：不愿意，必须一直 XInput** → 只能停在方案 C（只报连接状态），或者接受方案 B 的脆弱实现。

> 我的建议：**A**。做成"模式自适应"：DInput 下显示百分比，XInput 下显示「2.4G 连接 · 无电量数据」，两种状态都正确，不用你操心当前在哪个模式。

### Q2 精度够用线在哪？

- 精确到 1%（需要厂商通道）
- 只要"满 / 中 / 低 / 空"三档也认（XInput 本来就有四档，只是被 WIRED 掩盖了 —— 但**当前这个接收器连四档都是假的**，全是满档）

> 我的建议：**要 1%**。三档在 60% 附近没有分辨率，做不了"还剩多久"。

### Q3 能不能接受"必须开着 Space Station"？

方案 B 依赖它，且它的管道是单实例、随时可能改版。你如果平时不开 Space Station，方案 B 直接作废。

> 我的建议：**不接受**。把电量显示建立在一个第三方 Electron 应用的私有 IPC 上，升级一次就碎。

## 4. 四条路，摊开对比

| | A. 走 DInput 模式的厂商通道 | B. 借用 Space Station 的管道 | C. 只报连接状态（现状） | D. 卸载飞智驱动 |
|---|---|---|---|---|
| 能否拿到百分比 | ✅ 能（需一次真机验证） | ⚠️ 能，但要看别人脸色 | ❌ 不能 | ✅ 大概率能 |
| 用户代价 | 打游戏要切回 XInput | 必须常开 Space Station | 无 | **失去驱动与 XInput** |
| 稳定性 | 中（依赖固件协议） | **低**（单实例 IPC、随时改版、Electron 一升级就断） | 高 | 低（不可逆的操作） |
| 实现成本 | 中（协议适配 + 模式识别） | 高（要 hook libuv 才能拿到双向报文） | 0（已完成） | 低但**不建议** |
| 结论 | **推荐作为可选增强** | 不做 | **默认基线** | 不做 |

### 为什么 B 判死刑（补充证据）

管道是单实例（`ERROR_PIPE_BUSY`），我们**连不进去**，只能：
1. 抢在 Space Station 之前占管道做代理 —— 要改启动顺序，且它一升级就崩；
2. hook Electron 主进程的 `uv_write` / `uv_read_start` 拿双向报文 —— 能拿到协议，但**依然发不出命令**（管道被占），只解决了"知道 cmdId"这一半问题。

也就是说：**B 路线拿到协议也没用，我们还需要一条能发命令的通道** —— 而那正是我们一开始缺的东西。这是它被判死刑的根本原因，不是成本问题。

### 为什么 D 不做

卸载驱动确实可能让 dongle 退回"标准 HID + 厂商集合"，但代价是用户失去手柄的全部自定义功能，且恢复要靠重装驱动。**为了一个百分比不值得**，也不该由我们替用户做这个决定。

## 5. 推荐路线

**基线（已实现，不动）**：方案 C。XInput 模式下显示「2.4G 连接 · 暂无电量」，绝不编数字。
**增强（本次设计）**：方案 A，做成**可选、可回落**的一等公民：

```
手柄当前模式      读到的通道            界面显示
─────────────────────────────────────────────────────────────
XInput（2.4G）   只有 045E:028E        「2.4G 连接」+ 暂无电量   ← 现状
DInput           2BDF:xxxx 厂商集合    「2.4G · 62%」            ← 新增
有线 USB         厂商集合（待验证）    「有线 · 充电中 · 62%」    ← 新增
未连接           无                     「未连接」
```

关键点：**同一份配置，两种模式都能正确表达**，用户不需要知道自己在哪个模式。

## 6. 方案 A 的技术设计

### 6.1 先做一次验证实验（30 分钟，需要你配合）

这一步没做完，后面都是空谈。要确认的只有一件事：**DInput 模式下的厂商通道，能不能读到百分比。**

1. 你把手柄切到 **DInput**（背面开关，或按手册的长按组合）
2. 我跑 `tools/usb_probe.py list`，确认是否出现 `2BDF` 的 0xFF00/0xFF01 厂商接口
3. 对那个接口写 `05 EC`（V1）与 `03 5A A5 01 02 00`（V2），各抓 32/64 字节应答
4. 拿 Space Station 上显示的数字去对表 —— **对上了才算证据**（就像迈从那次用 100% 对表一样）

**如果对不上**：方案 A 作废，基线就是终态，我会把这条结论写进 README 的"已知限制"，不再反复折腾。

### 6.2 若验证通过，实现形态

**不动架构，只加一个协议分支**。现有 `vendor_query` 已经支持"命令模板 + 帧尾校验 + 应答前缀 + 电量偏移 + presence"，
飞智的两套协议都能用它表达（如果 V2 需要 32 字节定长帧，`report_length` 已经支持）。

```
devices.json
  flydigi-apex4
    protocol.name = "vendor_query"
    command        = "05 EC"                 # V1；V2 则 "03 5A A5 01 02 00"
    report_length  = 32
    reply_prefix   = "05 EC"                 # 应答首两字节回显命令
    level_offset   = <待测>
    charging_byte  = <待测>
    link           = "wireless"
```

配置表达不了的部分，才动代码（预计只有一处）：**"该设备有多个可选协议，按现场能力择一"**。
现有 `read_device` 已经是"多候选接口 + 遇到失败换下一个"的结构，加一个 `protocols: [...]`
数组即可复用同一套循环，不需要新概念。

### 6.3 模式识别与回落（不靠猜）

不做"猜你现在是什么模式"，而是**让读取结果自己说话**：

- 厂商接口存在且应答有效 → 有电量
- 只有 `045E:028E` → XInput 模式，走 `xinput` 分支，`level=None`
- 两者都不在 → 未连接

也就是：**同一台设备允许配两个 protocol，谁通就用谁**。这条规则对以后所有"一机多形态"的设备都成立
（罗技接收器/有线已经是这个模式了，只是当年写死在 `logitech_hidpp` 分支里）。

### 6.4 失败路径

| 情况 | 行为 |
|---|---|
| DInput 下厂商接口不应答 | 回落 XInput 分支 → 显示连接状态，不报错弹窗 |
| 切模式过程中读到半截 | 走已有的"一次失败保留旧值"，不闪 |
| 固件改版导致字节偏移变了 | 只改 `devices.json`，不改代码 |
| 电量读到 0 | 用 `presence` 规则判"已关机"，不显示 0%（同漫步者那套） |
