# 飞智冰原狼 4 电量读取 — 需求澄清与设计方案（v5）

> 状态：**电量与充电状态仍然读不到，但 2.4G / 有线 / 未连接 三态已经可以通过 USB 端口区分。**  
> 网络调研 + 多轮真机验证都做完了：电量数字和充电标志不在 USB 报文里，
> 但接收器与有线手柄各占不同的物理端口，Windows 把端口写进了注册表，
> 因此链路可以老实地区分开。  
> 日期：2026-10-20　基线：`9ebbd5f`

---

## 0. 结论先行

**手柄在 2.4G 和"直连数据线"两种接法下，都没有把电量交给系统的任何通道 —— 不是我们读得不对，是数据不在那儿。**

| 项目 | 结果 |
|---|---|
| 2.4G / 有线 / 未连接 三态区分 | ✅ **已实现** —— 通过 USB 注册表端口判别 |
| 电量百分比 | ❌ 硬件不输出，官方与第三方都确认 |
| 无线充电状态（放底座） | ❌ 硬件不上报，15002 帧零变化 |
| 有线充电状态（插数据线） | ✅ **已实现** —— 插线即 USB 供电，界面显示「有线 · 充电中」 |

**仍然不能读的**：电量百分比、底座上的充电状态。
**可以读的**：设备当前接在哪个 USB 端口 → 推断是 2.4G 接收器还是有线直连。
它的电量只有一种物理表达——**手柄上的指示灯**（低电量闪红），而指示灯永远不会进入 USB 报文。

所以**读电量/充电状态这条路仍然完全堵死**。但另一个事实同样确凿：
接收器和有线手柄虽然共用同一个 USB 设备实例 ID（`045E:028E\FLYDIGI_DIREWOLF_4`），
但它们实际插在不同的 USB 端口上；Windows 把当前端口写进了注册表
`LocationInformation`（例如 `Port_#0011.Hub_#0001` 与 `Port_#0005.Hub_#0001`）。
**端口不同，链路就不同。**

> ⚠️ 一个容易误判的坑：**接收器与手柄直连时用的是同一个 VID:PID 和序列号**  
> （都是 `045E:028E\FLYDIGI_DIREWOLF_4`），所以插上线之后 PnP 看起来"毫无变化"。  
> 本次测试前你已拔掉接收器，因此测到的确实是有线手柄本人。

> 第 12 条是本轮最硬的证据：**不是命令猜错了，是这个接口根本不接受写入。**

### 最后一轮：连"控制传输"这条路也堵死（2026-10-20，2.4G 实连）

前两轮用的是 hidapi 的 `hid_write()`，它走**中断 OUT 端点**——而该端点不存在。
但 HID 还有另一条独立通路：**控制传输**上的 `SET_REPORT` / `SET_FEATURE`，
它和描述符里的 `OUT=0` 不是一回事，值得单独试。

做法：绕开 hidapi，用 `CreateFileW` 直接拿内核句柄（成功，`GENERIC_READ|GENERIC_WRITE`），
再调 `HidD_SetOutputReport` / `HidD_SetFeature` / `HidD_GetInputReport` / `HidD_GetFeature`。

| # | 事实 | 证据 |
|---|---|---|
| 13 | 句柄能拿到，但**读取全部失败** | `HidD_GetInputReport` 在 16/32/64/65 字节四种长度下**全部 FAIL**；`HidD_GetFeature` 对 report 0x00/01/02/03/10/11/12 **全部 FAIL** |
| 14 | **控制传输 SET_REPORT 被驱动拒绝** | 6 条命令 × 64/65 两种长度共 12 次，全部 `err=1` |
| 15 | **控制传输 SET_FEATURE 同样被拒绝** | 6 条命令全部 `err=1` |
| 16 | 设备自己也不广播电量 | 2.4G 实连时被动监听，只有标准手柄帧 |

> `err=1` = **ERROR_INVALID_FUNCTION**。
> 这不是"我们的程序没权限"或"命令格式不对" —— 是 **Windows 的 HID 类驱动**
> 核对报告描述符后主动拒绝：描述符里根本没声明输出/特性报告。
> 到此为止，用户态能走的路（中断 OUT / 控制传输 SET_REPORT / SET_FEATURE / GET_REPORT）
> **全部试完并全部失败**。再往下只能动驱动（N1 明令不做）。

### 一处必须纠正的错误

上一版方案里我把 `2BDF:028A` 当成了"飞智接收器本体"，**这是错的**。  
PnP 显示它是一个 **HIK 2K 摄像头**：

```
USB\VID_2BDF&PID_028A&MI_00  → HIK 2K Camera      (usbvideo)
USB\VID_2BDF&PID_028A&MI_02  → HIK 2K Camera-Audio (usbaudio)
USB\VID_2BDF&PID_028A&MI_04  → USB 串行设备 COM3   (usbser)
USB\VID_2BDF&PID_028A&MI_06  → HID-compliant device (HidUsb)
```

它手柄关机时也在、对它发 `05 EC` 只回一个计数器 ack —— 全都解释得通了。  
**这条线索作废**，我之前"2BDF 是飞智另一个设备"的推断也是错的。

## 3. 网络调研：飞智的接收器有两代，我们这台是"没有厂商通道"的那一类

| 接收器                       | VID:PID                            | 接口结构                                                                                     | 有没有厂商通道        |
| ------------------------- | ---------------------------------- | ---------------------------------------------------------------------------------------- | -------------- |
| 第一代（Apex 3/4、Vader 3）     | `04B4:2412`（Cypress）               | 接口 2 = 厂商协议                                                                              | ✅ 有            |
| 第二代（Vader 5 Pro、Apex 5/6） | `37D7:2401`                        | 0=XInput、1=扩展输入（32 B `5a a5 ef` 帧，需主机开 test mode）、2=**厂商定义 HID Feature**（0x10/0x11/0x12） | ✅ 有，且能过 WebHID |
| **冰原狼 4 随附接收器**           | **`045E:028E\FLYDIGI_DIREWOLF_4`** | **单接口，只有 XInput**                                                                        | ❌ **没有**       |

依据：

- PadForge 的设备表把 `04B4:2412` / `37D7:2501,2502,2401` 列为飞智两代手柄；
- `flydigi-back-buttons-macos-bridge` 项目明确写了 37D7 接收器的三接口结构，以及"电量通过 WebHID 配置页读取"；
- 本机 `Get-PnpDevice` 过滤 `37D7` → **零结果**；冰原狼 4 的接收器只有 `045E:028E` 一个实例、没有 `MI_xx` 子接口 ——  
  说明它是一块**只做 Xbox 360 模拟**的廉价 dongle，厂商把配置/电量通道整个省掉了。
- 佐证：官方手册的排障条目写着 *"Software Not Recognizing Controller: Connect the controller via **wired mode** to establish initial communication"* ——  
  飞智自己也是让用户插线来跟手柄通信的。

**所以：不是我们没找到命令，是这颗 dongle 上根本没有那条线 —— 直连手柄也一样。**

## 5. 最终方案：电量读不到，但 2.4G / 有线 / 未连接 三态可区分

**没有数字可读时，就不显示数字；但链路是真实可判的，所以让界面把链路说清楚。**

### 5.1 三态实现结果

| 想显示的状态 | 能否实现 | 判据 / 证据 |
|---|---|---|
| **2.4G 连接** | ✅ | 设备出现在配置里的 `wireless_port`（`Port_#0011.Hub_#0001`） |
| **有线 · 充电中** | ✅ | 设备出现在其它端口；插线即由 USB 供电，官方驱动也显示充电图标 |
| **未连接** | ✅ | `XInputGetState` 失败 / HID 接口消失（`rc=1167 ERROR_DEVICE_NOT_CONNECTED`） |
| 底座上无线充电 | ❌ | 硬件不上报，15002 帧零变化，不能编 |
| 电量百分比 | ❌ | 硬件不输出，官方与第三方都确认 |

### 5.2 为什么「有线 · 充电中」敢写

插数据线时，手柄由 USB 总线供电；Space Station 同时显示充电图标。
这不是从手柄报文里读出来的充电标志，而是从「有线连接」推出的合理结论：
**USB 数据线同时承载数据和电源，能枚举成功就意味着在供电。**

这跟罗技鼠标的处理一致：插线时显示「有线 · 充电中」，不插线时按实际电池状态。

### 5.3 为什么底座充电仍然只显示「2.4G 连接」

手柄放底座充电时，它和电脑的通信仍走 2.4G 无线链路。
我们之前关掉「底座智能启停」做过对比：15002 帧与平时逐字节相同，
XInput 报告也一致 —— **硬件不上报任何充电标志**。

既然读不到，就不能编。底座充电时界面保持「2.4G 连接」，不说「充电中」。

### 5.4 实现要点

```
来源优先级（同一台设备，谁有数据用谁）
  ① 有厂商通道 / 电量页 / 充电标志 → 读（这台都没有）
  ② 从注册表读 USB 端口，判别链路   ← 这台落在这里
  ③ 链路也判别不出 → 只显示「暂无电量」
```

新增 / 改动：
- `app/core/usb_port.py`：读 `HKLM\SYSTEM\CurrentControlSet\Enum\USB\VID_...&PID_...\serial\LocationInformation`
- `app/core/protocols.py`：`_apply_port_link()` —— 匹配 HID 信息 → 读端口 → 判 `wireless`/`wired`
- `app/config/devices.json`：飞智的 `link` 改为
  `{"mode":"port","wireless_port":"Port_#0011.Hub_#0001","wired_charging":true}`

> ⚠️ 关键依赖：`wireless_port` 必须是你底座/接收器所在的端口。
> 这个值写入内置模板，基于本次实测的 `Port_#0011.Hub_#0001`。
> 如果你以后把底座插到别的 USB 口，需要在设置里重新校准（当前版本未做 UI，
> 但配置结构已预留）。

## 6. 实测结论（三种物理接法逐个排除）

### 6.1 直连数据线：已验证，**没有通道**

| 步骤 | 结果 |
|---|---|
| 1. 拔掉接收器，手柄用原装数据线直连电脑 | ✅ 完成 |
| 2. 跑 `usb_probe.py list`，看有无新厂商接口 | ❌ **没有任何新接口**，仍是 `045E:028E` 一个 |
| 3. 发 `05 EC` / `03 5A A5 01 02 00` | ❌ **7 条命令全部 `rc=-1` 写入失败** |
| 4. 拿 Space Station 对表 | — 无应答可对 |

→ **这条路关掉了。** 直连和 2.4G 是同一套 XInput 呈现，都没有下行能力。

### 6.2 充电底座：出局

你平时是这么接的（所以它一度是条新线索：底座自己可能是个带厂商接口的 USB 设备）：

```
电脑 ──原装线──> 充电底座 ──┬── 2.4G 接收器（插在底座上）
                        └── 手柄（放在底座上充电）
```

但你随后补充了决定性的一条：**手柄放上去就会自动休眠，只有拿起来才连接。**

→ 底座与手柄之间只有供电触点、没有数据通道。
底座最多知道"我在给东西充电"，不可能知道电量百分比；
而且读到的也只是"手柄睡着时"的电量，你打游戏时它根本不在底座上。

**所以底座这条不用测了，直接出局。** 三种物理接法全部排除：

| 接法 | 打游戏时能读吗 |
|---|---|
| 2.4G 接收器（你的日常） | ❌ |
| 手柄直连数据线 | ❌ |
| 经充电底座 | ❌ |

### 6.3 蓝牙：实测连不上

你按蓝牙模式配对，**电脑始终无法连接上手柄**。这条路你说不行，那就跳过。

### 6.4 网络交叉验证：官方和第三方都确认"这台就没有电量数字"

这是最有说服力的一环 —— 不是我们搞不定，是**这台硬件本来就不输出电量**：

| 来源 | 原文 |
|---|---|
| 什么值得买 冰原狼4 vs 北通鲲鹏20 横评 | "电量显示：北通可设置按键查看剩余电量，并通过不同灯光颜色区分档位；**飞智无法查看具体电量，仅在低电量时亮红灯提醒**。" |
| 飞智官方说明书（Direwolf 4 User Manual） | "**Low Power: The indicator light flashes red**" —— 电量状态的**唯一**表达就是指示灯闪红 |
| 官方 Space Station 功能列表 | 按键映射 / 宏定义 / 陀螺仪映射 / 摇杆调节 —— **没有任何电量项** |

**结论：第三方横评、官方说明书、官方软件三方一致 —— 冰原狼 4 不提供电量百分比。**

### 6.5 端口：唯一还能用的信号（新增）

电量和充电标志确实不在 USB 报文里，但我们发现另一个可观测的事实：
**接收器和有线手柄共用同一个 USB 设备实例 ID，因此 Windows 里同一个设备节点
只能有一个"主人"；当连接方式切换时，注册表里的 `LocationInformation`
（即 USB 端口）会跟着切换。**

实测时间线（后台持续读取 `hid.enumerate()` 与注册表）：

```
[   0.0s]  IG=['01']  LOC='Port_#0011.Hub_#0001'  ADDR=11   ← 2.4G（接收器在底座）
[  38.9s]  IG=[]      LOC='Port_#0011.Hub_#0001'  ADDR=11   ← 拔线/切换中
[  39.4s]  IG=[]      LOC='Port_#0005.Hub_#0001'  ADDR=5    ← 注册表已更新
[  39.7s]  IG=['02']  LOC='Port_#0005.Hub_#0001'  ADDR=5    ← 有线（手柄直连）
[  53.2s]  IG=[]      LOC='Port_#0005.Hub_#0001'  ADDR=5    ← 拔线/切换中
[  54.4s]  IG=['01']  LOC='Port_#0011.Hub_#0001'  ADDR=11   ← 回到 2.4G
```

这说明：

1. `IG_01` / `IG_02` 不是判据（和端口相关，不代表设备类型）
2. **端口是稳定判据**：`Port_#0011` = 底座/接收器，`Port_#0005` = 数据线/手柄
3. 注册表 `LocationInformation` 随当前活跃设备实时更新，无需驱动级访问

于是链路可区分：端口匹配 → 2.4G；端口不匹配 → 有线。
而有线时手柄由 USB 供电，官方驱动显示充电图标，因此「有线 · 充电中」成立。

### 6.6 最终结论

> **电量百分比和充电标志仍然读不到** —— 2.4G / 直连 / 底座三种接法都试过，
> 控制传输在内的四条用户态通路全部堵死，蓝牙实测连不上，

## 9. 一句话总结

**飞智冰原狼 4 不输出电量百分比，也不输出无线充电标志 —— 这是硬件与固件的设计。**
官方说明书里电量状态的唯一表达是"低电量时指示灯闪红"，
而指示灯永远不会变成 USB 报文。

但我们**可以区分 2.4G / 有线 / 未连接三种链路状态**：
接收器和有线手柄虽然共用同一个 USB 设备实例 ID，却占不同的物理端口；
Windows 把端口写进注册表 `LocationInformation`。

**处理方式**：
- 2.4G 接收器 → 「2.4G 连接」
- 数据线直连（USB 供电） → 「有线 · 充电中」
- 休眠/关机 → 「未连接」
- 底座无线充电 / 电量百分比 → 硬件不上报，界面不说谎

| 想显示 | 结果 |
|---|---|
| 2.4G 连接 | ✅ |
| 未连接 | ✅ |
| 有线 · 充电中 | ✅ |
| 底座无线充电 | ❌ 硬件不上报，15002 帧零变化 |
| 电量百分比 | ❌ 硬件不输出，官方与第三方都确认没有 |
