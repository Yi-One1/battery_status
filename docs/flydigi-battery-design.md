## 0. 结论先行

**手柄在 2.4G 和"直连数据线"两种接法下，都没有把电量交给系统的任何通道 —— 不是我们读得不对，是数据不在那儿。**

| 连接方式 | 能否读电量 | 状态 |
|---|---|---|
| 2.4G 接收器（你的日常） | ❌ | 已实测；连**控制传输**也 `ERROR_INVALID_FUNCTION` |
| 手柄**直连数据线**到电脑 | ❌ | 已实测，同样无通道 |
| 经**充电底座** | ❌ | 已排除 —— 手柄放上去就休眠，底座与手柄无数据通道 |
| **蓝牙** | ❌ | **你实测连不上** |
| **控制传输** SET_REPORT / SET_FEATURE | ❌ | 已实测，被 HID 类驱动拒绝（`err=1`） |

**外加一条来自外部的决定性佐证：官方和第三方都确认这台手柄没有电量数字输出。**
它的电量只有一种物理表达——**手柄上的指示灯**（低电量闪红），而指示灯永远不会进入 USB 报文。

七条彼此独立的证据（见第 1 节）都指向同一件事：手柄在 2.4G 与直连两种模式下，  
Windows 里都只有一个由微软 `xusb22` 驱动接管的标准 Xbox 360 手柄接口，  
它没有输出端点、没有 feature 端点、也没有厂商 Usage Page。  
**没有下行通道，就意味着发不出任何"报一下电量"的请求。**

> ⚠️ 一个容易误判的坑：**接收器与手柄直连时用的是同一个 VID:PID 和序列号**  
> （都是 `045E:028E\FLYDIGI_DIREWOLF_4`），所以插上线之后 PnP 看起来"毫无变化"。  
> 本次测试前你已拔掉接收器，因此测到的确实是有线手柄本人。

| 2 | 手柄接入后，PnP 里**只多出一个**设备               | `USB\VID_045E&PID_028E\FLYDIGI_DIREWOLF_4`，单接口（没有 `MI_xx`，不是复合设备），服务 = `xusb22`              |

| 4 | WinRT 的两套手柄 API 都看不到它                | `Windows.Gaming.Input.Gamepad.Gamepads` → 0；`RawGameController` → 0（xusb22 设备不在 WinRT 枚举范围）  |
| 5 | Space Station 的通道是**单实例命名管道**，外部连不进去 | `CreateFileW("\\\\.\\pipe\\fcs.sock")` → `err=231 ERROR_PIPE_BUSY`                           |

| 7 | 协议本身是公开的，但我们没有通道去发                   | SDL `SDL_hidapi_flydigi.c`：V1 `05 EC`、V2 `03 5A A5 01 02 00`                                 |

### 本次新增：直连数据线后的实测（2026-10-20，接收器已拔掉）

| # | 事实 | 证据 |
|---|---|---|
| 8 | 直连后 PnP 里**没有多出任何新设备** | 仍是 `USB\VID_045E&PID_028E\FLYDIGI_DIREWOLF_4` 一个，父节点 `USB\ROOT_HUB30` 的 `Port_#0011`；只挂了一个 `IG_01` 子接口 |
| 9 | 唯一那个 HID 接口仍是**输入专用** | `UP=0x0001 U=0x0005`（通用桌面 / 游戏手柄）、`IN=15 / OUT=0 / FEAT=0` |
| 10 | 手柄**不会自己广播电量** | 被动监听 12 秒收到 12004 帧，**全部是同一帧** `00 80 ff 7f 00 80 ff 7f 00 80 00 00 00 00`（标准手柄报告，摇杆居中） |
| 11 | **强行读 feature report 全部为空** | 逐个读 report 0–20 → 无一个返回数据 |
| 12 | **下发的 7 条命令全部写入失败** | `05 EC`、`05 EC`+62B、`03 5A A5 01 02 00`（含 64B 版）、`03 5A A5 00 01 00`、`5A A5 03 01 02 00`、`00` → **一律 `rc=-1`** |

> 第 12 条是本轮最硬的证据：**不是命令猜错了，是这个接口根本不接受写入。**
> `OUT=0 / FEAT=0` 的硬件能力摆在那里，换任何命令都一样。

### 最后一轮：连"控制传输"这条路也堵死（2026-10-20，2.4G 实连）

前两轮用的是 hidapi 的 `hid_write()`，它走**中断 OUT 端点**——而该端点不存在。
但 HID 还有另一条独立通路：**控制传输**上的 `SET_REPORT` / `SET_FEATURE`，
它和描述符里的 `OUT=0` 不是一回事，值得单独试。

做法：绕开 hidapi，用 `CreateFileW` 直接拿内核句柄（成功，`GENERIC_READ|GENERIC_WRITE`），
再调 `HidD_SetOutputReport` / `HidD_SetFeature` / `HidD_GetInputReport` / `HidD_GetFeature`。

| # | 事实 | 证据 |
|---|---|---|
| 13 | 句柄能拿到，但**读取全部失败** | `HidD_GetInputReport` 在 16/32/64/65 字节四种长度下**全部 FAIL**；`HidD_GetFeature` 对 report 0x00/01/02/03/10/11/12 **全部 FAIL** |
| 14 | **控制传输 SET_REPORT 被驱动拒绝** | 6 条命令 × 64/65 两种长度共 12 次，全部 `err=1` |
| 15 | **控制传输 SET_FEATURE 同样被拒绝** | 6 条命令全部 `err=1` |
| 16 | 设备自己也不广播电量 | 2.4G 实连时被动监听，只有标准手柄帧 |

> `err=1` = **ERROR_INVALID_FUNCTION**。
> 这不是"我们的程序没权限"或"命令格式不对" —— 是 **Windows 的 HID 类驱动**
> 核对报告描述符后主动拒绝：描述符里根本没声明输出/特性报告。
> 到此为止，用户态能走的路（中断 OUT / 控制传输 SET_REPORT / SET_FEATURE / GET_REPORT）
> **全部试完并全部失败**。再往下只能动驱动（N1 明令不做）。

### 一处必须纠正的错误

上一版方案里我把 `2BDF:028A` 当成了"飞智接收器本体"，**这是错的**。  
PnP 显示它是一个 **HIK 2K 摄像头**：

```
USB\VID_2BDF&PID_028A&MI_00  → HIK 2K Camera      (usbvideo)
USB\VID_2BDF&PID_028A&MI_02  → HIK 2K Camera-Audio (usbaudio)
USB\VID_2BDF&PID_028A&MI_04  → USB 串行设备 COM3   (usbser)
USB\VID_2BDF&PID_028A&MI_06  → HID-compliant device (HidUsb)
```

它手柄关机时也在、对它发 `05 EC` 只回一个计数器 ack —— 全都解释得通了。  
**这条线索作废**，我之前"2BDF 是飞智另一个设备"的推断也是错的。

## 2. 目标 / 非目标（按你的新要求重述）

**目标**

- G1 手柄在**正常打游戏的状态**（2.4G / XInput）下，尽量让界面上的信息有用
- G2 绝不显示假数据（不猜、不按时长估算、不把满档当 100%）

> 结果上 N3 被完整保住了：你现在的用法（2.4G）一个字都不用改。

## 3. 网络调研：飞智的接收器有两代，我们这台是"没有厂商通道"的那一类

| 接收器                       | VID:PID                            | 接口结构                                                                                     | 有没有厂商通道        |
| ------------------------- | ---------------------------------- | ---------------------------------------------------------------------------------------- | -------------- |
| 第一代（Apex 3/4、Vader 3）     | `04B4:2412`（Cypress）               | 接口 2 = 厂商协议                                                                              | ✅ 有            |
| 第二代（Vader 5 Pro、Apex 5/6） | `37D7:2401`                        | 0=XInput、1=扩展输入（32 B `5a a5 ef` 帧，需主机开 test mode）、2=**厂商定义 HID Feature**（0x10/0x11/0x12） | ✅ 有，且能过 WebHID |
| **冰原狼 4 随附接收器**           | **`045E:028E\FLYDIGI_DIREWOLF_4`** | **单接口，只有 XInput**                                                                        | ❌ **没有**       |

依据：

- PadForge 的设备表把 `04B4:2412` / `37D7:2501,2502,2401` 列为飞智两代手柄；
- `flydigi-back-buttons-macos-bridge` 项目明确写了 37D7 接收器的三接口结构，以及"电量通过 WebHID 配置页读取"；
- 本机 `Get-PnpDevice` 过滤 `37D7` → **零结果**；冰原狼 4 的接收器只有 `045E:028E` 一个实例、没有 `MI_xx` 子接口 ——  
  说明它是一块**只做 Xbox 360 模拟**的廉价 dongle，厂商把配置/电量通道整个省掉了。
- 佐证：官方手册的排障条目写着 *"Software Not Recognizing Controller: Connect the controller via **wired mode** to establish initial communication"* ——  
  飞智自己也是让用户插线来跟手柄通信的。

**所以：不是我们没找到命令，是这颗 dongle 上根本没有那条线 —— 直连手柄也一样。**

## 5. 最终方案：接受现状，只显示链路

既然没有数字可读，就不该有数字 —— 这也正是本项目一贯的原则。

| 情形                 | 电量    | 状态行                    |
| ------------------ | ----- | ---------------------- |
| 手柄拿起、2.4G 连接       | --    | 2.4G 连接                |
| 手柄放上底座（休眠）         | --    | 未连接                    |
| 手柄关机               | --    | 未连接                    |

这就是**当前代码的行为**：第一轮已经修掉了"虚构充电中"的 bug，
现在它不会撒谎，只会老实说"2.4G 连接"。

```
来源优先级（同一台设备，谁有数据用谁）
  ① 有厂商通道 → 读（这台没有）
  ② 有电量页   → 读（这台没有）
  ③ 都没有     → 只显示链路，不显示数字   ← 这台落在这里
```

**改动量：0。** 不需要动 `devices.json`、不需要改 `protocols.py`、不需要加缓存字段。

## 6. 实测结论（三种物理接法逐个排除）

### 6.1 直连数据线：已验证，**没有通道**

| 步骤 | 结果 |
|---|---|
| 1. 拔掉接收器，手柄用原装数据线直连电脑 | ✅ 完成 |
| 2. 跑 `usb_probe.py list`，看有无新厂商接口 | ❌ **没有任何新接口**，仍是 `045E:028E` 一个 |
| 3. 发 `05 EC` / `03 5A A5 01 02 00` | ❌ **7 条命令全部 `rc=-1` 写入失败** |
| 4. 拿 Space Station 对表 | — 无应答可对 |

→ **这条路关掉了。** 直连和 2.4G 是同一套 XInput 呈现，都没有下行能力。

### 6.2 充电底座：出局

你平时是这么接的（所以它一度是条新线索：底座自己可能是个带厂商接口的 USB 设备）：

```
电脑 ──原装线──> 充电底座 ──┬── 2.4G 接收器（插在底座上）
                        └── 手柄（放在底座上充电）
```

但你随后补充了决定性的一条：**手柄放上去就会自动休眠，只有拿起来才连接。**

→ 底座与手柄之间只有供电触点、没有数据通道。
底座最多知道"我在给东西充电"，不可能知道电量百分比；
而且读到的也只是"手柄睡着时"的电量，你打游戏时它根本不在底座上。

**所以底座这条不用测了，直接出局。** 三种物理接法全部排除：

| 接法 | 打游戏时能读吗 |
|---|---|
| 2.4G 接收器（你的日常） | ❌ |
| 手柄直连数据线 | ❌ |
| 经充电底座 | ❌ |

### 6.3 蓝牙：实测连不上

你按蓝牙模式配对，**电脑始终无法连接上手柄**。这条路你说不行，那就跳过。

### 6.4 网络交叉验证：官方和第三方都确认"这台就没有电量数字"

这是最有说服力的一环 —— 不是我们搞不定，是**这台硬件本来就不输出电量**：

| 来源 | 原文 |
|---|---|
| 什么值得买 冰原狼4 vs 北通鲲鹏20 横评 | "电量显示：北通可设置按键查看剩余电量，并通过不同灯光颜色区分档位；**飞智无法查看具体电量，仅在低电量时亮红灯提醒**。" |
| 飞智官方说明书（Direwolf 4 User Manual） | "**Low Power: The indicator light flashes red**" —— 电量状态的**唯一**表达就是指示灯闪红 |
| 官方 Space Station 功能列表 | 按键映射 / 宏定义 / 陀螺仪映射 / 摇杆调节 —— **没有任何电量项** |

**结论：第三方横评、官方说明书、官方软件三方一致 —— 冰原狼 4 不提供电量百分比。**

### 6.5 最终结论

> **2.4G / 直连 / 底座三种接法都试过，加上控制传输在内的四条用户态通路全部堵死，
> 蓝牙实测连不上，而官方与第三方都确认这台手柄不存在电量数字输出。**
>
> 它的电量信息只有一种物理表达：**手柄上的指示灯**（低电量闪红）。
> 这个信息永远不会进入 USB 报文，所以任何软件都读不到。

**这条路到此结束，不再投入。**

| 接法 | 打游戏时能读吗 |
|---|---|
| 2.4G 接收器（你的日常） | ❌ |
| 手柄直连数据线 | ❌ |
| 经充电底座 | ❌ |
| 蓝牙 | ❌ 实测连不上 |
| 控制传输 SET_REPORT / SET_FEATURE | ❌ `ERROR_INVALID_FUNCTION` |
